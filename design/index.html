The interaction contract

Every control makes a promise: what it is, what it will do, and what happens after. Interaction design is keeping that promise under load, interruption, and failure. Visual polish cannot rescue a broken contract — it only makes the breakage more visible.

01

The contract

Users do not experience your design system. They experience a sequence of small negotiations: can I click this, what did that do, can I get back? Each unanswered question is a hesitation, and hesitations compound into abandonment.

  1. Every action gets a receipt. Immediate acknowledgment, then a persistent record of the result. Silence is indistinguishable from failure.
  2. Never surprise the user with a state they cannot leave. Modals close on Esc, destructive actions have an exit, errors keep the input.
  3. Prefer reversible to confirmed. Undo beats a dialog because it costs nothing to the 99% who meant it.
  4. Say what happened in the user's words. Not "Error 422." Not "Invalid input." What failed, why, and what to do next.
  5. Latency is a design material. Under 100ms say nothing; over 1s explain; over 10s let them leave.
  6. Keyboard is not an accessibility feature. It is a second input method that power users choose. If it is slower, the interaction is wrong.
The cost of a missing state

A missing loading state turns a 400ms request into a rage-click. A missing error state turns a recoverable validation failure into a lost form. Neither shows up in a happy-path demo, which is exactly why they ship broken.

02

Seven questions

Every interactive element must answer these, in this order, without the user thinking. One unanswered question is enough to make an interface feel unreliable.

# Question Answered by
1 What is this? A label, an icon with a text label, a familiar shape. Never an unlabelled glyph alone.
2 Can I use it right now? Enabled / disabled styling that is honest, plus a reason when disabled.
3 What happens if I do? Predictable label — a verb and an object: "Save draft", "Delete 3 listings".
4 Did it work? Immediate feedback, then a persistent result that does not vanish in 2 seconds.
5 Can I undo it? Undo affordance for anything not trivially repeatable.
6 What did it cost me? Price, credits, seats, time — stated before the action, not after.
7 Where am I now? Current location in nav, breadcrumbs, page title, preserved scroll and filters.
Run this as a checklist on the primary flow only. If the primary flow answers all seven, the rest usually follows.
03

Affordance

An affordance is what an object lets you do. A signifier is the evidence. Interfaces fail when they have the affordance without the signifier — a clickable div that looks like text — or the signifier without the affordance.

Rules

  • Clickable things look clickable. A button needs a boundary, a surface, or a weight that static text does not have. Underlines mean links; buttons mean actions.
  • Hover is not a signifier. On touch there is no hover. Anything discoverable only by hovering is hidden from half your users.
  • Cursor is a hint, not a contract. cursor: pointer on a non-interactive element is a lie that a keyboard user cannot even see.
  • Hit area ≥44×44px. WCAG 2.2 allows 24px with sufficient spacing; 44px is still the human answer. Extend small icons with padding or a pseudo-element, not by enlarging the glyph.
  • No dead zones. If a card is clickable, the whole card is clickable — except controls nested inside it, which must stop propagation.
  • Selected is not the same as hovered. A selected row keeps its mark when the pointer leaves.
The squint-and-click test

Blur the screenshot. Can you still tell the three clickable things from the twelve readable ones? If not, the signifiers are decoration rather than structure.

04

Feedback & latency

Three thresholds decide what you owe the user. Getting the pattern wrong is worse than showing nothing, because a spinner on a 90ms request teaches people the app is slow.

Time What the user thinks What to give them
0–100ms "Instant." Nothing. A press state is enough; an indicator here makes it feel slower.
100ms–1s "Still flowing." Immediate press state, then a subtle indicator only after ~300–500ms.
1–10s "Working on it." Determinate progress when estimable; a skeleton that matches the final layout.
10s+ "Is this broken?" Real progress, a cancel path, and the ability to leave and return.
Demo 01 · Three feedback strategies, 1.2s latency
Ready

Silent: 1.2 seconds of nothing, then a result — most users click again. Spinner: honest but heavy for a routine save. Optimistic: instant, with a quiet reconciliation and a real rollback on failure. The right answer depends on how often it fails.

Optimistic, pessimistic, hybrid

  • Optimistic when failure is rare and rollback is cheap and visible — likes, reorder, mark-as-read, rename. Never for payments, deletions, or anything a user would screenshot as proof.
  • Pessimistic when the server can reject for a reason the user must act on — booking a slot, submitting an application.
  • Hybrid — optimistic, with a quiet "Saving…" and a real, non-destructive error state. Mature products converge here.

In all three, the result must survive: a toast that disappears is not a receipt. Persist the new state in the interface, not only in a floating message.

05

Nine states of a view

A screen has more than a happy path. Teams that design nine states ship interfaces that survive reality; teams that design two ship demos.

State What it must show Common failure
First load Skeleton matching final geometry Spinner in a void; content jumps on resolve
Refreshing Existing data + subtle activity Blanking the screen to reload
Empty (new user) What this is for + one action "No data" with no path forward
Zero results (filtered) Which filter excluded what + clear Empty state that implies the data does not exist
Partial What loaded, what did not, retry for the gap Failing the whole page for one widget
Error Plain cause + retry + support path "Something went wrong" with no action
Offline Stale badge + retry when back Silent stale data presented as live
Permission denied Why + who can grant it Generic 403 or a blank page
Success What changed + next step Confetti and no indication of what to do now
Empty and zero-results are different states. Merging them is the most common state bug in search and filtering.
Cheap test

Toggle a network throttle, then break the endpoint on purpose. If the screen becomes a blank rectangle or an infinite skeleton, you have found the state you never designed — and so has every user on a train.

06

Forms

A form is the highest-friction surface in any product. Every unnecessary field, ambiguous label, and late error is a tax on the one thing the user came to do.

Structure

  • One column. Multi-column forms break the reading path and cause skipped fields.
  • Labels above fields, always visible. Placeholders are not labels: they disappear exactly when the user needs them.
  • Group in fieldsets when fields belong together, and order by the user's mental model, not the database schema.
  • Ask only what you will use. Every optional field reduces completion; every required-but-unused field is a dark pattern.
  • Mark optional, not required. If most fields are required, the asterisk is noise — label the exceptions.

Validation

  • Validate on blur after the user leaves a field, not on every keystroke — unless you can be certain the input is complete (e.g. a 4-digit code).
  • Don't disable the submit button. A disabled button tells the user nothing about what is missing. Let them submit, then show the first error and focus it.
  • Never clear the form on error. Preserve every value; preserve the scroll position; keep the user's place.
  • Error adjacent, not only at the top. For long forms, do both: an error summary with links, and inline messages.
  • Wire the semantics: aria-invalid, aria-describedby pointing at the message, and a live region for the summary.
  • Right keyboard: type="email", inputmode="numeric", autocomplete="one-time-code". Guessing the field type is a silent tax on mobile.
The single biggest form win

Preserve state. Users forgive a confusing label; they do not forgive retyping six fields because the server rejected the seventh.

07

Navigation

Orientation is a promise about location. Break it once and users start opening links in new tabs to avoid losing their place — a behaviour that is a direct measurement of distrust.

  • Current location is marked in the primary nav, not just implied by the page title.
  • Back works. Every in-app navigation pushes history; modals and tabs decide deliberately whether they do. A drawer that hijacks Back is a trap.
  • Deep links resolve. Filters, tabs, sort order and pagination belong in the URL, or they cannot be shared or restored.
  • Unsaved changes are guarded — in-app, and with beforeunload for real data loss. A guard on a search box is hostile; a guard on a half-written application is minimum viable care.
  • Scroll and filters survive the round trip. Returning from a detail view to the top of an unfiltered list is a data-loss event from the user's point of view.
  • Search is a last resort, not a navigation strategy. If users must search to find a primary destination, the nav is wrong.
08

Destructive actions

The default for anything reversible should be undo, not a confirmation dialog. Confirmation is a tax on every user to protect a few — and it trains people to click through dialogs without reading.

Demo 02 · Pick the pattern
Recommended

Undo toast, 8 seconds. Apply immediately, show "Listing archived · Undo".

Why: reversible and low-cost. A modal here adds friction to a routine tidy-up and teaches people to dismiss dialogs reflexively.

The pattern is a function of reversibility, blast radius, and frequency — not of how nervous the action makes the designer.

Situation Pattern Copy rule
Reversible, single item Undo toast, 5–10s State the result, offer undo, do not ask first.
Reversible, bulk Undo + count in the label "Archived 12 listings · Undo" — always the number.
Hard to reverse, single Confirm with the object named "Delete 'Summer internship'?" not "Are you sure?"
Irreversible, account-level Type-to-confirm + grace period Require the account email or project name, then a 24–72h delay.
Access revocation Confirm + explain effect Name who loses what, and when.
Never use OK/Cancel. The buttons must name the action: "Delete listing" / "Keep listing".

Colour alone is not a warning. A red button with the label "Continue" is less safe than a neutral button that says "Delete permanently" — the words carry the meaning, colour carries the emphasis.

09

Keyboard & focus

Focus is the cursor of the keyboard user. If it is invisible, misplaced, or trapped, the entire interface becomes a guessing game played blind.

  • Focus-visible ring: 2px, 2px offset, 3:1 against both surfaces. Never outline: none without a replacement.
  • Tab order follows visual order. If CSS reorders the layout, the DOM order must match or the tab order lies.
  • Modals trap focus, then return it to the element that opened them. Esc closes. The first focusable element inside receives focus, not the close button by reflex.
  • Composite widgets use roving tabindex — tabs, menus, grids get one tab stop, then arrow keys inside. Tabbing through 40 rows is not navigation.
  • Skip link as the first focusable element, pointing at main content.
  • Shortcuts are discoverable via a "?" panel, and never override browser or screen-reader combinations.
  • Every drag has a keyboard path. Reordering with the mouse only is an accessibility failure, not a limitation.
The 60-second test

Unplug the mouse. Complete the primary task with Tab, Shift+Tab, Enter, Space and Esc. Wherever you get stuck is a real defect, not a nice-to-have.

10

Gestures & pointer

Gestures are fast, invisible, and undiscoverable. They are an accelerator for people who already know the interface — never the only way to do something.

  • Every gesture has a visible alternative. Swipe-to-delete needs a menu item; pull-to-refresh needs a button.
  • Thresholds: commit a swipe past ~40% of the row or on sufficient velocity; below that, snap back. Never commit on a 4px accidental drag.
  • Show intent before commit. A dragged row reveals the trash target; it does not delete on release with no preview.
  • Hover only where hover exists — @media (hover: hover) and (pointer: fine). On touch, :hover latches after a tap and reads as a stuck selection.
  • Cancel zones: drag far enough away and release to abort, with a visible cue that it will abort.
  • Do not hijack scroll. Horizontal swipe on a vertically scrolling page is ambiguous and usually wrong.
  • Touch targets inside gestures are still 44px. A small handle is a missed swipe.

Error copy

An error message is the moment trust is either repaired or lost. It has one job: let the user fix the problem without leaving the screen.

The formula: what happened + why + what to do now. Keep the user's input, keep the tone neutral, and never blame them for a system constraint.

The formula

// what happened · why · what to do · preserve their work
headline: "We couldn't save your changes"
detail:   "The connection dropped. Your draft is still here."
action:   "Try again" + "Copy draft"
  • No blame words: invalid, illegal, forbidden, you must, you failed.
  • No codes alone: keep the code for support, put the meaning first.
  • No dead ends: every error has an action or an explanation of why none is possible.
  • No fake reassurance: "Oops!" is not an apology and does not help.
12

Trust & honesty

Interaction design is where dark patterns become executable. The rule is simple: the interface must not make a decision easier to make than it is to understand.

Pattern What it does Honest alternative
Confirmshaming "No thanks, I don't want to grow my career" Neutral decline: "Not now".
Roach motel One-click signup, support-ticket cancellation Cancel in the same number of steps as subscribe.
Fake urgency Countdown that resets on refresh Real deadline, real date, no timer.
Hidden cost Fees revealed at the final step Total price on the first screen that shows a price.
Preselected add-ons Insurance, newsletter, upsell ticked by default Unchecked, opt-in, plainly labelled.
Fake scarcity "3 people are viewing this" generated randomly Real inventory, or nothing.
Nagging Repeated modal until accepted Ask once; remember the answer.
The review question

Would you be comfortable explaining this screen to the user, out loud, with your name attached? If the honest answer is no, it is not a growth tactic — it is a liability with a conversion rate.

13

Anti-slop

Twelve interaction tells that make an interface feel like a prototype someone forgot to finish.

Tell What it signals, and the fix
Toast-only errors The message disappears before it can be read or acted on. Inline, persistent, adjacent.
No loading state The user clicks twice and creates a duplicate. Preserve geometry, acknowledge in 100ms.
Disabled submit with no reason A dead end with no diagnosis. Allow submit, then explain.
Form resets on error Data loss. Preserve every field, always.
Confirm dialog on everything Trains click-through. Undo instead.
Hover-only actions Invisible on touch and to keyboard users. Always-on menu or a visible button.
Modal on modal Lost context, broken Esc, focus chaos. Route to a page or replace the first modal.
Infinite skeleton Loading as a permanent design. Time out into an error with retry.
Mystery-meat navigation Icons with no labels. Add text, or a tooltip plus aria-label.
Auto-advancing carousel Moves while reading, fails on hover, inaccessible. Manual controls only.
Invisible focus outline: none with no replacement. Keyboard users are lost.
Fake empty state "No results" when a filter is hiding data. Say which filter, offer clear.

What this skill refuses to call interaction design

  • Confirmation dialogs used instead of undo
  • Latency hidden behind animation
  • Disabled controls used instead of explanation
  • Modals used for navigation
  • Hover used to carry essential actions
  • Success measured by clicks the user did not intend
